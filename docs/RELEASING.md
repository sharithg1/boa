# Releasing Boa

A release is a `vX.Y.Z` tag on `main`. Pushing the tag runs
`.github/workflows/release.yml`, which publishes a GitHub Release with:

| Asset | What |
|---|---|
| `Boa_X.Y.Z_macos-aarch64.dmg`, `…_macos-aarch64.app.zip` | Desktop app for Apple Silicon |
| `Boa_X.Y.Z_macos-x86_64.dmg`, `…_macos-x86_64.app.zip` | Desktop app for Intel Macs |
| `SHA256SUMS` | SHA-256 of every asset (`shasum -a 256 -c SHA256SUMS --ignore-missing`) |

Release notes are generated by GitHub from the merged PRs and commits since
the previous tag, grouped by PR label (`.github/release.yml`); edit them on
the release page afterwards if needed.

## CI

`.github/workflows/ci.yml` runs on every pull request and push to `main`:

- **rustfmt + version check**: `scripts/check-version.sh` (Cargo.toml and
  tauri.conf.json agree) and `cargo fmt --check`.
- **clippy + test (macOS)**: clippy with `-D warnings`, `cargo nextest run
  --profile ci` (`.config/nextest.toml`) and doctests. The Postgres
  integration tests skip themselves unless `PGHOST` is set.
- **desktop UI (typecheck, lint, test)**: `pnpm typecheck`, `pnpm lint`
  (Biome) and `pnpm test` (Vitest) in `crates/boa-desktop/ui`.

`main` has a ruleset requiring a pull request and these three checks.

## Cutting a release

**From GitHub:** Actions → **Cut release** → Run workflow (on `main`), pick
the bump from the dropdown: `patch` (default), `minor` or `major`. The next
version is computed from `[workspace.package] version` in the root
`Cargo.toml` (`0.1.16` → `0.1.17` / `0.2.0` / `1.0.0`; from a prerelease
such as `0.2.0-rc.1`, `patch` releases `0.2.0` and `minor` / `major` bump
the base to `0.3.0` / `1.0.0`). To release something else, e.g. a
prerelease, type an exact version (`0.2.0-rc.1`, no leading `v`) in the
optional version field; it overrides the bump. Tick "Dry run" to only see
the bump; the run summary shows the resolved version either way. It runs
`scripts/release.sh` on `main`, pushes the "Release vX.Y.Z" commit and the
tag; the tag push starts the Release workflow. Because the `main` ruleset
requires pull requests and green CI, the workflow pushes with the
`RELEASE_DEPLOY_KEY` secret, a write deploy key the ruleset lets bypass
(`GITHUB_TOKEN` cannot bypass rulesets on a personal repo, and its pushes
would not trigger Release either). Pushing from a laptop works as a repo
admin, who also bypasses.

**From a laptop**, on an up-to-date, clean `main` with green CI:

```sh
scripts/release.sh 0.1.5 --dry-run   # show what changes, touch nothing
scripts/release.sh 0.1.5             # bump, commit "Release v0.1.5", tag v0.1.5
git push --atomic origin main v0.1.5 # the script prints this; it never pushes
```

`scripts/release.sh` sets the version in the root `Cargo.toml`
(`[workspace.package]`, inherited by the desktop crate) and in
`crates/boa-desktop/tauri.conf.json`, refreshes `Cargo.lock`, commits
and creates an annotated tag. It refuses a version that is not newer than
the current one, a dirty tree, a branch other than `main` (unless
`--allow-branch`), an existing tag, or a `main` behind `origin/main`. To
undo before pushing: `git tag -d v0.1.5 && git reset --hard HEAD~1`.
(`crates/boa-desktop/ui/package.json` has its own unused `0.1.0`; it is
not part of the release version.)

The workflow then:

1. **version**: `scripts/check-version.sh vX.Y.Z` fails the run unless the
   tag, `Cargo.toml` and `tauri.conf.json` all say `X.Y.Z`, and decides the
   signing policy (see [Signing and notarization](#signing-and-notarization)).
2. **CI**: the whole CI workflow (`ci.yml`, called as a reusable workflow)
   on the release commit (tags do not trigger CI by themselves); nothing is
   published unless it passes.
3. **app** (aarch64 and x86_64, both built on an Apple Silicon runner):
   `pnpm tauri build --target <triple> --bundles app,dmg`, then checks
   `Info.plist`'s version and the signature.
4. **publish**: writes `SHA256SUMS`, uploads everything into a **draft**
   release (`--generate-notes`), downloads the draft's assets back and
   compares their checksums, then publishes the draft. Tags with a suffix
   (`v0.2.0-rc.1`) become pre-releases. Re-running a failed run replaces an
   unpublished draft, but never touches a published release: its assets are
   what users downloaded. To replace a published release, delete it on
   GitHub first (or, better, cut a new version).

Builds are reproducible from the tag: Rust is pinned by `rust-toolchain.toml`
and every build uses the committed `Cargo.lock` (`--locked`, or `cargo fetch
--locked` before `tauri build`). Bump the toolchain in its own PR so CI
checks it.

Pull requests that change `release.yml`, `scripts/check-version.sh` or
`tauri.conf.json`, and manual runs on a branch (Actions → Release → Run
workflow), do steps 1 and 3 without publishing (no step 2: pull requests get
CI from `ci.yml` itself). A manual run on a tag runs CI and publishes, which
is how Cut release starts it. The app builds are kept as workflow artifacts.

If the tag check or CI fails (tagged the wrong commit, forgot the bump, a
broken test): delete the tag locally and on GitHub
(`git push origin :refs/tags/vX.Y.Z`), fix, and tag again.

## Signing and notarization

**Policy.** A stable tag (`vX.Y.Z`, no suffix) must be signed with a
Developer ID and notarized: the run fails before publishing if any of the
six secrets below is missing. Pre-release tags (`v0.2.0-rc.1`), pull
requests and branch runs sign when the secrets exist and fall back to an
ad-hoc signature otherwise. To publish unsigned stable releases on purpose
(no Apple Developer account yet), set the repository **variable**
`ALLOW_UNSIGNED_RELEASES` to `true` (Settings → Secrets and variables →
Actions → Variables); the run summary then says "signing: optional". It is
currently set.

With an ad-hoc signature (`APPLE_SIGNING_IDENTITY=-`) the bundle is sealed
but not from an identified developer, so macOS blocks the downloaded app
("cannot be opened" / "is damaged"). Users clear the quarantine flag once
after installing:

```sh
xattr -dr com.apple.quarantine /Applications/Boa.app
```

(or right-click → Open, or System Settings → Privacy & Security → Open
Anyway, depending on the macOS version).

Repository secrets (Settings → Secrets and variables → Actions):

| Secret | Value |
|---|---|
| `APPLE_CERTIFICATE` | base64 of the "Developer ID Application" certificate + key exported as `.p12` (`base64 -i cert.p12 \| pbcopy`) |
| `APPLE_CERTIFICATE_PASSWORD` | the `.p12` export password |
| `APPLE_SIGNING_IDENTITY` | e.g. `Developer ID Application: Your Name (TEAMID)` |
| `APPLE_ID` | Apple ID email used for notarization |
| `APPLE_PASSWORD` | an app-specific password for that Apple ID |
| `APPLE_TEAM_ID` | the 10-character team ID |
| `RELEASE_DEPLOY_KEY` | private half of the "Cut release workflow" write deploy key |

With the first three the app is signed; with all six Tauri also notarizes
and staples it. The run summary says which mode was used.

## Building release artifacts locally

```sh
cd crates/boa-desktop/ui && pnpm install
pnpm tauri build --bundles app,dmg                              # this Mac's arch
pnpm tauri build --target x86_64-apple-darwin --bundles app,dmg # Intel (rustup target add x86_64-apple-darwin)
```

Output is under `target/release/bundle/` (`target/<triple>/release/bundle/`
with `--target`).
